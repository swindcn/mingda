# 熔炼时长与设备占用排程设计

## 背景与目标

当前熔炼配方只维护材质、炉型、成分和配料信息，炉次只保存“计划出炉时间”。系统无法计算一炉生产对熔炼设备的完整占用区间，也无法在同一设备一天安排多次连续熔炼时识别时间冲突。

本次增加配方标准时长和炉次计划时间区间，用于：

- 根据配方自动计算预计完成时间；
- 形成可追溯的设备计划占用区间；
- 支持同一设备按时间连续安排多个炉次；
- 对重叠计划进行提示和二次确认，而不是强制禁止；
- 为后续设备日历、班次产能和实际执行偏差分析提供基础数据。

本阶段不建设完整设备甘特图，不计算班次累计产能，也不引入设备停机、维护或换型日历。

## 方案选择

采用“配方标准时长 + 炉次时长快照 + 炉次占用区间”的方案。

不采用炉次实时读取配方时长。已下达炉次必须保存当时使用的时长快照，避免配方升级后历史计划时间发生变化。

不在本阶段建设独立设备排程日历。设备占用判断基于炉次自身的计划开始和预计完成时间完成，后续可平滑扩展。

## 配方模型

`MeltRecipe` 增加三个整数分钟字段：

- `meltingDurationMinutes`：熔炼时长；
- `transferDurationMinutes`：转运时长；
- `cleaningDurationMinutes`：清炉时长。

### 校验规则

1. 三个字段均必填，必须是大于等于 `0` 的整数。
2. 三项合计必须大于 `0`。
3. 新建、编辑、克隆和新版本必须完整保存或复制三个字段。
4. 已生效配方仍遵循现有状态机，不能直接编辑。需要先停用，再编辑形成下一版本草稿。
5. 历史配方迁移时三个字段默认 `0`，避免迁移失败。
6. 三项合计为 `0` 的历史配方不能用于新合炉排产，接口提示先维护配方时长。
7. 配方列表不强制增加三个独立列，避免主表过宽；查看和编辑页面展示完整时长，并可在列表按需要展示“总占用时长”。

### 管理端交互

配方基本信息区增加三个 `InputNumber`：

- 标签分别为“熔炼时长（分钟）”“转运时长（分钟）”“清炉时长（分钟）”；
- 同一行三列展示；
- 最小值为 `0`，只允许整数；
- 表单实时显示三项合计的“标准设备占用时长”。

## 炉次模型

`HeatOrder` 增加：

- `plannedStartAt`：计划开始时间；
- `calculatedFinishAt`：根据配方时长自动计算的原始预计完成时间；
- `plannedFinishAt`：最终预计完成时间，允许人工调整；
- `meltingDurationMinutesSnapshot`：熔炼时长快照；
- `transferDurationMinutesSnapshot`：转运时长快照；
- `cleaningDurationMinutesSnapshot`：清炉时长快照；
- `occupancyDurationMinutesSnapshot`：三项标准时长合计快照；
- `finishTimeAdjusted`：预计完成时间是否被人工调整。

### 兼容字段

现有 `plannedOutputAt` 暂时保留，并在新炉次中同步保存为 `plannedFinishAt`，保证现有列表、详情和既有接口调用不立即失效。

新功能的业务判断统一使用 `plannedStartAt` 和 `plannedFinishAt`。后续完成兼容迁移后，可单独规划移除 `plannedOutputAt`。

### 时间计算

```text
occupancyDurationMinutesSnapshot
= meltingDurationMinutesSnapshot
+ transferDurationMinutesSnapshot
+ cleaningDurationMinutesSnapshot

calculatedFinishAt
= plannedStartAt + occupancyDurationMinutesSnapshot
```

默认：

```text
plannedFinishAt = calculatedFinishAt
finishTimeAdjusted = false
```

用户修改预计完成时间后：

```text
plannedFinishAt = 用户填写值
finishTimeAdjusted = plannedFinishAt != calculatedFinishAt
```

`plannedFinishAt` 必须晚于 `plannedStartAt`。修改配方或计划开始时间后，前端重新计算并覆盖预计完成时间，用户可以再次手动调整。

## 设备占用与冲突规则

### 占用区间

设备占用采用左闭右开区间：

```text
[plannedStartAt, plannedFinishAt)
```

因此上一炉预计完成时间等于下一炉计划开始时间时，不构成冲突。

### 参与冲突判断的炉次

- `WAITING`：参与；
- `IN_PROGRESS`：参与；
- `COMPLETED`：不参与新计划冲突；
- `CANCELED`：不参与。

本阶段冲突以计划占用区间为准。实际生产超时影响后续计划的能力，留待设备执行和动态调度阶段扩展。

### 冲突条件

同一设备下，已有炉次满足以下条件时发生冲突：

```text
existing.plannedStartAt < candidate.plannedFinishAt
AND existing.plannedFinishAt > candidate.plannedStartAt
```

### 软校验与二次确认

冲突不直接禁止下达，采用两阶段确认：

1. 前端选择设备、配方、计划开始和预计完成时间后，调用冲突检查接口。
2. 页面展示冲突炉次编号、状态、计划开始和预计完成时间。
3. 首次创建炉次时，后端在事务内再次查询冲突。
4. 若存在冲突且请求未携带确认标识，后端返回 `409` 和结构化冲突清单，不创建任何数据。
5. 前端弹出确认框，用户确认后携带 `confirmScheduleConflict: true` 重新提交。
6. 第二次提交时后端必须再次查询冲突，避免两次请求之间出现新计划。
7. 携带确认标识后允许创建，但仍保留容量、材质、配方、设备、班组和工单剩余数量等强校验。
8. 强制下达行为写入炉次 `CREATED` 过程记录，payload 保存冲突炉次编号、冲突区间和确认人。

## 后端 API

### 配方接口

现有配方列表、详情、新增、修改、克隆和新版本接口增加三个时长字段。所有写接口执行整数、非负和总时长校验。

### 排产选项

`GET /admin/production/melt-pool/options` 的配方选项增加：

```text
meltingDurationMinutes
transferDurationMinutes
cleaningDurationMinutes
occupancyDurationMinutes
durationConfigured
```

历史配方总时长为 `0` 时仍可在管理端识别，但在合炉排产中标记不可使用，并提示维护配方时长。

### 冲突检查

新增：

```text
POST /admin/production/heat-orders/check-conflicts
```

请求：

```json
{
  "furnaceCode": "EQ-MELT-IF-1T-01",
  "plannedStartAt": "2026-08-13T08:00:00+08:00",
  "plannedFinishAt": "2026-08-13T09:30:00+08:00"
}
```

响应返回冲突炉次数组，不产生副作用。接口用于提前提示，不能替代创建事务内的最终检查。

### 创建炉次

`POST /admin/production/heat-orders` 请求调整为：

```text
plannedStartAt
plannedFinishAt
confirmScheduleConflict
```

后端根据选择的已生效配方重新读取三个时长，生成时长快照和 `calculatedFinishAt`。前端不能提交或覆盖时长快照。

后端判断 `plannedFinishAt` 是否与自动计算值不同，并生成 `finishTimeAdjusted`。

创建事务继续使用 `Serializable`，并在同一事务内完成：

- 工单剩余数量复核；
- 单炉容量复核；
- 材质、配方、设备、班组关系复核；
- 配方时长复核；
- 设备时间冲突复核；
- 炉次、分配明细、数据归属和操作记录创建。

## 管理端合炉排产

将原“计划出炉时间”调整为：

- “计划开始时间”：必填；
- “预计完成时间”：必填，默认自动计算，允许修改。

交互顺序：

1. 选择目标熔炼设备；
2. 选择已生效且已配置时长的配方；
3. 选择执行班组；
4. 输入计划开始时间；
5. 系统自动计算预计完成时间；
6. 用户可修改预计完成时间；
7. 页面异步显示设备时间冲突；
8. 提交时如有冲突弹出二次确认。

页面同时展示：

- 熔炼时长；
- 转运时长；
- 清炉时长；
- 标准占用时长；
- 最终计划占用区间；
- 冲突炉次提示。

修改配方或计划开始时间时，重新计算预计完成时间并清除旧冲突检查结果。快速切换配方、设备或时间时，旧请求不得覆盖新状态。

## 炉次列表与详情

炉次列表增加或替换为：

- 计划开始；
- 预计完成；
- 设备占用时长；
- 时间冲突标识。

炉次详情展示：

- 配方三个时长快照；
- 自动预计完成时间；
- 最终预计完成时间；
- 是否人工调整；
- 下达时确认的冲突炉次信息。

历史炉次如果没有新时间字段，继续展示原“计划出炉时间”，不参与新的设备冲突判断。

## 权限与数据范围

- 冲突检查复用 `production.schedule.view` 或排产列表权限；
- 创建和冲突确认均要求 `production.schedule.create`；
- 冲突确认不是独立权限，属于下达炉次过程的一部分；
- 冲突清单只返回当前用户有权查看的必要炉次字段，不返回无关业务数据；
- 后端创建时仍检查目标设备上的全部有效占用，不能因数据行权限看不到冲突炉次而漏检。

## 并发与错误处理

1. 冲突检查接口只提供提示，不能保证提交时仍无冲突。
2. 创建炉次必须在事务内重新检查。
3. 两个用户同时安排同一设备重叠时间时：
   - 未确认冲突的请求返回 `409`；
   - 已明确确认的请求允许创建；
   - 所有强校验仍然生效。
4. 结构化冲突响应必须区分普通业务错误，前端只在明确的排程冲突时弹出二次确认。
5. 二次确认请求失败时不自动重试，不产生前端假成功。

## 数据迁移

1. 配方三个时长字段使用非空整数并默认 `0`。
2. 炉次新增时间和快照字段初期允许为空，以兼容历史数据。
3. 现有 `plannedOutputAt` 不删除。
4. 当前测试环境没有有效炉次时不需要回填；若正式部署前存在历史炉次，迁移脚本不得根据当前配方反向生成历史时长快照。
5. Prisma 迁移必须同时在本地临时测试 schema 和测试服务器执行验证。

## 测试计划

### 配方

- 三个时长均为非负整数时可保存；
- 负数、小数和三项合计为 `0` 时拒绝；
- 克隆和新版本完整复制时长；
- 历史零时长配方不能用于新排产；
- 配方升级不改变已下达炉次的时长快照。

### 时间计算

- 计划开始 `08:00`，时长 `60 + 15 + 15`，自动完成为 `09:30`；
- 人工改为 `09:45` 后设备占用结束为 `09:45`；
- 修改计划开始或配方后重新自动计算；
- 完成时间早于或等于开始时间时拒绝；
- 前后端跨时区计算结果一致。

### 冲突判断

- 区间部分重叠、完全包含和被包含均识别冲突；
- 新开始等于上一炉结束不冲突；
- 新结束等于下一炉开始不冲突；
- 不同设备不冲突；
- 已取消、已完成炉次不冲突；
- 待生产、生产中炉次参与冲突；
- 首次提交冲突返回 `409` 且不创建数据；
- 二次确认后允许创建并记录冲突信息；
- 二次提交时新增冲突能够被重新读取并记录。

### 既有排产规则

- 单炉容量、工单剩余数量和材质一致性继续生效；
- 配方必须已生效并绑定目标设备；
- 班组必须属于设备车间；
- 并发分配同一工单不能超分；
- 测试继续使用临时 PostgreSQL schema，不影响业务数据。

### 管理端

- 自动完成时间、人工修改、时长摘要和冲突提示正确；
- 快速切换设备、配方和时间不会回写旧结果；
- 冲突二次确认只出现一次，取消后不创建炉次；
- 刷新失败和确认失败时不能重复或假成功；
- 列表和详情正确展示时间快照与人工调整标识。

## 后续扩展

本设计提供设备计划占用区间。后续可增加：

- 工厂日历和班次内可用时间；
- 设备维护、停机和不可用时段；
- 实际开始、实际结束与计划偏差；
- 生产中超时对后续炉次的动态预警；
- 设备甘特图和拖动调整；
- 自动寻找下一可用开始时间。

这些能力应复用 `plannedStartAt`、`plannedFinishAt` 和时长快照，不改变本期已定义的占用区间语义。
