# 熔炼配方停用修改与版本升级设计

## 目标

允许已生效熔炼配方在停用后继续修改。修改保存时自动升级主版本号，修改后的配方回到草稿，重新提交生效后才能用于后续生产业务。

## 状态机

```text
草稿 DRAFT --提交生效--> 已生效 ACTIVE
已生效 ACTIVE --停用--> 已停用 DISABLED
已停用 DISABLED --编辑保存并升级版本--> 草稿 DRAFT
```

- 草稿：允许查看、编辑、删除、复制、提交生效。
- 已生效：允许查看、复制、停用；不允许编辑、删除。
- 已停用：允许查看、复制、编辑；不允许删除或直接提交生效。
- 已停用配方只有实际保存成功后才升级版本并回到草稿，打开或取消编辑不改变数据。

## 版本规则

- 继续使用同一条配方记录和同一配方编码，不为新版本生成新配方编码。
- 自动递增主版本：`V1.0 -> V2.0 -> V3.0`。
- 版本解析仅接受 `V<主版本>.0` 格式；历史异常格式不能自动升级时，后端返回明确错误，要求先修正版本。
- 草稿普通编辑不升级版本；只有从 `DISABLED` 状态保存时升级一次。
- 保存成功后状态变为 `DRAFT`，后续多次编辑该草稿不会重复升级。

## 权限与接口

- 前端已停用记录显示“编辑”按钮，使用现有 `model.recipe.edit` 权限。
- 后端 `PUT /admin/modeling/recipes/:code` 同时接受 `DRAFT` 和 `DISABLED`：
  - `DRAFT` 保存：保留版本和状态。
  - `DISABLED` 保存：忽略前端提交的版本值，按数据库当前版本自动递增，并将状态设为 `DRAFT`。
- `ACTIVE` 状态继续拒绝修改，必须先调用停用接口。
- 前端表单在编辑停用配方时显示下一版本号预览，但最终版本以后端计算为准。

## 数据关联

- 配方编码不变，因此材质牌号、适用炉型、目标成分、配料关系及未来生产工单引用不需要迁移。
- 本方案只保留当前版本的数据，不提供历史版本快照。后续若生产工单需要追溯下达时的配方内容，应由工单保存配方版本和明细快照，不能依赖配方主档的当前内容。

## 测试

- 已生效配方直接编辑返回错误。
- 已生效配方停用后可编辑。
- `V1.0` 停用后保存变为 `V2.0 + DRAFT`。
- 同一草稿再次保存仍为 `V2.0`。
- 重新生效、停用、保存后变为 `V3.0 + DRAFT`。
- 没有 `model.recipe.edit` 权限时，前端不显示编辑按钮，后端返回 403。
- 打开停用配方编辑后取消，不改变版本和状态。
