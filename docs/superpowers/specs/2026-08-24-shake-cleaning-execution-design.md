# 落砂清理执行设计

## 1. 目标与边界

本模块承接合型浇注报工，在生产工单锁定的工艺路线上执行单一 `OP-SHAKE / 落砂清理` 节点。现场操作分为“落砂”和“清理打磨”两个阶段，但工艺路线和生产工单进度只保留一个节点。

一期包含：

- 浇注合格箱数转换为待落砂毛坯件数。
- 冷却时长计算、未到期提醒和提前落砂记录。
- 落砂、清理打磨两阶段的多次报工、缺陷、设备和操作人追溯。
- 落砂合格件流入待清理队列，清理合格件生成毛坯产出批次。
- 管理端撤销和反向返还数量。
- 管理端和微信小程序的真实接口、权限和数据范围。

一期不包含：

- 冷却时长强制卡控或双人审批。
- 热处理、机加工和毛坯入库的执行页面。
- 自动生成落砂清理任务；任务来源为真实浇注报工队列。

## 2. 工艺与数据链

```text
MoldingReport
  -> PouringMoldBatch
  -> PouringReport
  -> ShakeBatch（待落砂毛坯批次）
  -> ShakeReport
  -> CleaningBatch（待清理批次）
  -> CleaningReport
  -> BlankOutputBatch（合格毛坯产出）
```

所有批次保留生产工单、产品、工单锁定路线版本、工艺节点、上游报工和操作人关系。不使用产品当前默认路线替代工单已锁定的历史路线。

浇注报工生成待落砂数量：

```text
待落砂毛坯件数 = PouringReport.goodQty × MoldingTask.cavityCountSnapshot
```

浇注废品箱不生成待落砂数量。穴数使用造型任务快照，不读取后续修改的模具档案。

## 3. 工艺路线配置

`ProcessRoutingNode` 新增 `coolingDurationMinutes` 非负整数，默认为 `0`。字段仅在工序为 `OP-SHAKE` 或所属工段为“清理”的路线节点上显示，单位为分钟。

工单已锁定路线版本后，浇注报工沿真实 `ProcessRoutingEdge` 查找首个可达的落砂清理节点。无可达节点时浇注报工仍成功，但不生成待落砂队列。同层出现多个可达落砂节点时拒绝自动归属，避免批次进入错误分支。

## 4. 冷却提醒

```text
实际冷却分钟 = 落砂提交时间 - 浇注报工时间
剩余冷却分钟 = max(0, 要求冷却分钟 - 实际冷却分钟)
```

- 剩余时间大于零时显示红色“冷却未到期”和倒计时。
- 冷却到期后显示绿色“可落砂”。
- 一期不做权限卡控。未到期时用户确认风险即可提交。
- `ShakeReport` 必须保存要求冷却分钟快照、实际冷却分钟和 `earlyShake = true/false`，为后续主管授权卡控预留数据。

## 5. 落砂阶段

落砂报工支持多次提交，每次录入：

- 落砂合格件数。
- 落砂废品件数。
- 落砂设备。
- 绑定 `OP-SHAKE` 的缺陷代码及数量。
- 备注、操作人和操作时间。

报工消费数量为“合格 + 废品”，不得超过待落砂余量，且必须大于零。一次报工可跨同一任务的多笔待落砂批次，固定按“浇注报工时间 -> 批次 ID” FIFO 扣减。

每笔落砂报工的合格数生成一笔 `CleaningBatch`，废品不进入清理队列。

## 6. 清理打磨阶段

清理报工支持多次提交，每次录入：

- 清理合格件数。
- 清理废品件数。
- 切割浇冒口重量（kg，非负数）。
- 清理、抛丸、打磨或切割设备。
- 绑定 `OP-SHAKE` 的缺陷代码及数量。
- 备注、操作人和操作时间。

报工消费数量为“合格 + 废品”，不得超过待清理余量，且必须大于零。一次报工可按“落砂报工时间 -> 批次 ID” FIFO 消费多笔待清理批次。

每笔清理报工的合格数生成 `BlankOutputBatch`，保存完整上游追溯关系和工单锁定路线的下一节点。如果落砂清理是路线最后节点，毛坯批次状态为“待毛坯入库”。本期不直接更新生产工单最终完工数量。

## 7. 设备和缺陷

设备必须同时满足：

- `Furnace.status = 启用`。
- 已通过 `ProcessRoutingNodeEquipment` 绑定工单锁定路线的落砂清理节点。
- 落砂阶段的设备类型为“落砂”。
- 清理阶段的设备类型为“清理”、“抛丸”、“打磨”或“切割”。

设备类型使用现有“设备类型配置”字典值。管理端只使用下拉选择，小程序同时支持下拉和扫描设备编码。

落砂和清理共用绑定当前 `OP-SHAKE` 工序的缺陷代码。废品数大于零时必须填写缺陷，缺陷数量合计必须等于废品数，同一缺陷不得重复。

## 8. 状态与完成判断

聚合任务状态：

- `WAITING_SHAKE`：存在待落砂余量，尚无落砂消费。
- `SHAKING`：已部分落砂，仍有待落砂余量。
- `WAITING_CLEANING`：当前无待落砂余量，存在待清理余量且尚无清理消费。
- `CLEANING`：已部分清理，仍有待清理余量。
- `WAITING_POURING`：当前两类队列均为零，但上游浇注节点尚未完成。
- `COMPLETED`：上游浇注节点已完成，且所有有效待落砂和待清理余量都为零。

不允许仅因当前队列暂时清空就提前完成工艺节点。

## 9. 撤销、幂等和并发

- 每次落砂和清理提交都带页面实例级 `requestId`，同一任务和 `requestId` 重试不重复扣减。
- 批次和报工保存 `versionNo`。提交事务锁定任务与 FIFO 批次，旧版本返回 `409`。
- 清理撤销按消费明细返还待清理数量，并将对应毛坯产出批次置为撤销。
- 落砂报工若已有有效清理消费，必须先撤销清理报工。撤销落砂时返还待落砂数量并撤销来源待清理批次。
- 浇注报工若已有有效落砂消费，必须先撤销落砂报工。
- 所有撤销保留原记录，记录撤销人、时间和原因，不物理删除。

## 10. 页面和权限

管理端新增“落砂清理”菜单，列表页签为“待落砂、落砂中、待清理、清理中、等待后续浇注、已完成”。详情页包含任务信息、落砂记录、清理记录和批次追溯。页面继续使用查询按钮右上角、`ResizableTable`、固定操作列和 `TableActions`。

小程序新增“落砂清理”入口，提供状态页签、任务扫码、下拉刷新、落砂报工和清理报工。数量输入支持 `-10/-1/+1/+10` 和一键拉满。

权限键：

- `production.shake_clean.view`
- `production.shake_clean.shake_report`
- `production.shake_clean.clean_report`
- `production.shake_clean.reverse`
- `mini.production.shake_clean.view`
- `mini.production.shake_clean.shake_report`
- `mini.production.shake_clean.clean_report`

后端是权限和数据范围的最终边界。前端隐藏只用于交互，不能代替接口守卫。小程序没有菜单权限时，不显示九宫格入口且不返回任务数据。

## 11. 测试验收

自动化必须覆盖：

1. 浇注合格箱数按工单锁定穴数转换为待落砂件数。
2. 浇注废品不进入待落砂队列。
3. 冷却未到期返回风险提醒，确认后可提交并保存提前落砂快照。
4. 落砂和清理均支持多次报工、FIFO 跨批次扣减和 `requestId` 幂等。
5. 数量超余量、错误设备类型、未绑定设备、错误工序缺陷和缺陷数量不符被后端拒绝。
6. 清理撤销返还待清理数量并撤销毛坯产出。
7. 落砂和浇注撤销遵循下游先撤销的顺序。
8. 上游未完成时队列清空显示“等待后续浇注”，不提前完成节点。
9. 管理端权限、小程序权限、下拉刷新、扫码和真实接口通过页面测试。
10. API、管理端、小程序构建通过，Docker PostgreSQL 与 API 完成真实接口回归。
